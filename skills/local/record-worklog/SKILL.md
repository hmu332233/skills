# Record worklog

AI와 함께한 저장소 작업 세션을 두 층으로 기록한다. 코드나 문서만 봐서는 알 수 없는 동작, 함정, 시행착오를 남기는 것이 이 기록의 핵심 가치다.

- **세션이 기록의 정본이다.** 대화의 목표, 판단 변화, 결정과 알게 된 사실이 기록 범위를 정한다.
- **Raw log는 append-only history다.** 당시의 흐름, 결과, 검증, 실패한 시도를 보존하며 한 번의 기록 실행이 끝난 뒤에는 수정하지 않는다.
- **Knowledge는 living reference다.** 현재도 참인 결론만 주제별로 갱신한다.
- 같은 사실이 겹치면 knowledge가 현재 정본이고, log는 과거의 스냅샷이다.

## 1. 기록 위치 확정

기록은 `WORKLOG_ROOT/<repo>/` 아래에 쓴다. 두 값 모두 이 스킬 디렉터리의 `worklog.local` 파일에서 읽는다.

```text
# worklog.local 형식
root: <WORKLOG_ROOT 절대경로>
<저장소 루트 절대경로>: <repo 이름>
```

절차:

1. 기록 대상 저장소의 루트 경로를 확인한다. 사용자가 다른 저장소를 지정하지 않으면 현재 작업 디렉터리(`pwd`)의 Git 루트다. 코드 변경이 없었던 조사·설계 세션도 해당 저장소에 기록한다.
2. `worklog.local`의 매핑에 그 경로가 있으면 해당 `<repo>` 이름을 그대로 쓴다.
3. 없으면 사용자에게 "이 경로는 어떤 이름으로 기록할까요?"라고 묻고, 답을 `<경로>: <이름>` 한 줄로 `worklog.local`에 추가해 다음부터 묻지 않는다.
4. `root:`가 없으면 `WORKLOG_ROOT` 경로도 물어서 같은 방식으로 저장한다.

**완료 기준:** `WORKLOG_ROOT`와 `<repo>`가 확정되었고, 새로 답 받은 값은 `worklog.local`에 저장되었다.

## 2. 세션 복원

현재 대화와 이 세션에서 실행한 도구의 결과를 주된 근거로 사용한다. 대화를 그대로 전사하지 말고 다음 흐름을 복원한다.

- 사용자의 목표와 세션 중 바뀐 범위
- 함께 수행한 작업과 중요한 결정, 그 이유
- 새로 알게 된 사실과 바뀐 이해
- 시도, 오판, 막다른 길과 판단이 전환된 계기 — 코드뿐 아니라 도구·환경 차원의 시행착오도 포함한다
- 실제 실행한 검증과 그 결과
- 남은 불확실성이나 후속 과제

기록 범위는 세션의 목표와 흐름으로 정한다. 코드, 문서, 테스트 결과, `git diff`, status, commit은 세션에서 얻은 사실을 정확히 확인하거나 심볼·링크를 보강할 때만 필요한 만큼 참고한다. 세션과 무관한 작업 트리 변경은 기록에 섞지 않는다.

실행하지 않은 검증은 실행한 것처럼 쓰지 않는다. 세션 일부가 요약으로 압축되었으면 남아 있는 요약과 도구 결과를 사용하고, 복원할 수 없는 세부는 불확실성으로 남긴다. 날짜는 실행 환경의 현재 날짜와 시간대를 사용하고, 다른 작업일을 기록해야 할 때만 사용자에게 확인한다.

**완료 기준:** 최초 요청부터 현재 상태까지 중요한 결정, 알게 된 사실, 판단의 전환, 검증과 남은 불확실성이 모두 설명된다.

## 3. 저장소 기록 구조 준비

`WORKLOG_ROOT` 아래에 다음 구조를 사용한다.

```text
<WORKLOG_ROOT>/
├── <repo>/
│   ├── README.md
│   ├── knowledge/
│   └── log/
└── _shared/
    └── knowledge/
```

`_shared/knowledge/`는 여러 저장소에 실제로 걸친 지식이 생길 때만 만든다. 기존 구조에 호환되는 지침이나 템플릿이 있으면 그 형식을 유지한다. 새 `README.md`에는 최소한 `## Knowledge`와 `## Worklog` 인덱스를 만든다.

**완료 기준:** 이번 기록에 필요한 디렉터리와 인덱스가 존재하며 기존 문서를 덮어쓰지 않았다.

## 4. Raw log 작성

`<WORKLOG_ROOT>/<repo>/log/YYYY-MM-DD-<slug>.md`를 만든다. 같은 경로가 이미 있으면 기존 로그를 수정하지 말고 더 구체적인 slug를 사용한다.

```markdown
---
type: worklog
repo: <repo>
date: YYYY-MM-DD
tags: []
issues: []
changes: []
promoted_to: []
---

# <작업 제목>

## 세션 목표

## 작업과 결정

## 알게 된 사실

## 시도와 막다른 길

## 검증과 남은 불확실성

## 승격 후보

## 링크
```

결과만 요약하지 말고 결론에 도달한 과정을 보존한다. `시도와 막다른 길`에는 실패한 시도, 오판, 판단이 전환된 계기를 도구·환경 차원의 시행착오까지 포함해 남긴다. 사실, 당시의 판단, 아직 확인되지 않은 추정을 구분한다. 내용이 없으면 `승격 후보`, `링크` 섹션은 제거한다. `issues`와 `changes`는 세션과 직접 관련된 이슈, pull request, merge request 또는 commit이 있을 때만 채운다.

**완료 기준:** 다음 세션의 AI가 이 log만 읽어도 무엇을 왜 했고, 무엇을 알게 되었으며, 어디까지 확인했는지 복원할 수 있고 기존 log 파일은 변경되지 않았다.

## 5. Knowledge로 승격

각 승격 후보를 다음 기준으로 판정한다.

1. 이후 작업에서도 유용하다.
2. 세션의 명시적 결정이나 관련 자료로 근거가 확인된다.
3. 일회성 진행 상태가 아니라 계속 유지할 사실이다.

승격을 실행하기 전에 승격 후보 목록(각 후보의 요지와 대상 knowledge 문서)을 사용자에게 보여주고 확인을 받는다. 사용자가 제외한 후보는 log-only로 남긴다. 확인된 후보는 `<repo>/knowledge/`의 같은 주제 문서에 반영해 갱신한다. 같은 주제 문서가 없을 때만 새로 만든다. 여러 저장소에 공통인 사실은 `_shared/knowledge/`에 한 번만 기록하고 각 저장소 인덱스에서 표준 Markdown 상대 링크로 연결한다.

```markdown
---
type: reference
repo: <repo>
tags: []
created: YYYY-MM-DD
updated: YYYY-MM-DD
related_issues: []
related_changes: []
---

# <주제>

## 요약

## 현재 이해

## 제약과 함정

## 근거와 관련 코드

## 알게 된 과정
```

기존 knowledge를 갱신할 때 `created`는 보존하고 `updated`만 현재 날짜로 바꾼다. `related_issues`와 `related_changes`는 해당하는 것이 있을 때만 채운다. Shared knowledge에는 `repo` 대신 `repos: [<repo>, ...]`를 사용한다.

대화에서 형성된 결정과 히스토리는 해당 raw log로 연결한다. 코드에 관한 사실은 저장소 상대 경로와 심볼을 인용하고, 쉽게 낡는 라인 번호는 raw log에만 둔다. 기록 대상 저장소의 `docs/` 등에 정본이 있으면 knowledge에는 결론과 정본 링크만 둔다. 승격한 문서 경로를 raw log의 `promoted_to`에 기록한다. 승격할 사실이 없으면 빈 knowledge 문서를 만들지 않고 `promoted_to: []`를 유지한다.

**완료 기준:** 모든 승격 후보가 사용자 확인을 거쳐 승격 또는 log-only로 판정되었고, `promoted_to`가 실제 수정한 knowledge 문서와 정확히 일치한다.

## 6. 인덱스와 변경 검토

- 새 knowledge 문서를 `<repo>/README.md`의 `## Knowledge`에 한 번만 연결한다.
- 새 log를 `## Worklog`에 한 번만 연결한다.
- 모든 링크는 대상 파일에서 해석되는 상대 경로로 작성한다.
- 이번 log, 승격된 knowledge, 필요한 인덱스 외의 파일을 건드리지 않았는지 확인한다.
- 사용자가 명시적으로 요청한 경우에만 commit한다.

**완료 기준:** 새 문서를 인덱스에서 찾을 수 있고 링크가 유효하며, append-only 규칙을 지켰고 관련 없는 파일 변경이 없다.
